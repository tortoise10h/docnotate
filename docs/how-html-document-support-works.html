How HTML document support works

This page explains the change on this branch in two halves: how an .html file gets rendered in the app, and how comments and highlights still land on the exact right text. By the end you can review the diff with confidence.

Based on plans/html-document-support.md and the working tree as of this review.

1. Why you care

DocNotate already annotates markdown files. Users select text, add notes, and see green highlights. Agent-generated HTML files — reports, dashboards, explainers — could not join that flow. The app rejected them.

The hard part: markdown rendering is fully under our control. We rebuild the page from a stored node tree, so we can paint anchor ids onto every block. HTML files bring their own CSS and JavaScript. We must not rebuild them. So how do comments find their place?

The one-sentence answer. At parse time we tag every block element in the HTML with a random anchor id, store that annotated copy as the version's content, render it in a sandboxed iframe, and let the iframe and the app page talk through postMessage.

The annotation stack was never really about markdown. It only needs three things: blocks that carry ids in the DOM, a server-side node tree matching those ids, and a comment payload in JSON. This change satisfies those three needs in a new way. Nothing about the Comment model changes.

2. In one picture

Here is the whole system. The top path is the existing markdown flow. The bottom path is the new HTML flow. Both end in the same place: comments anchor to blocks in document_nodes.

The parsers differ, but storage shape and comment UI are shared. Only the HTML path adds a content row: an html_contents record holding annotated_html, linked from the version through a polymorphic content reference.

3. Walk through it — Part A: rendering

What happens between the user opening an .html file and seeing it on screen.

1

The open action accepts HTML. DocumentsController#open now calls Document.supported_file?. That method in Documents::FileTypeable accepts .html and .htm next to the markdown extensions.

2

The file syncs and parses as before. Documents::FileSyncable#open checks mtime and size. If the file changed, AstParseable#parse_ast_and_save! runs inside one transaction. It now picks the parser by type: HtmlParser for HTML, MarkdownParser for markdown.

3

The HTML parser tags blocks and builds nodes. HtmlParser parses the file with Nokogiri::HTML5 — the browser-like parser. It walks the body and, for every block-level element, writes data-docnotate-block="block-xxxxxxxx" onto the element. Same id format as markdown: block- plus 8 random hex characters.

4

Two artifacts leave the parser. First, DocumentNode rows — headings become heading nodes with a level, other blocks use the tag name as type. Second, the whole file, serialized with the ids inside, is stored in an html_contents row that the version points to as its content. Both happen in the same transaction, so ids always match.

5

The show page renders an iframe, not a node loop. show.html.erb branches: markdown keeps the existing node-tree paper; HTML renders _html_paper.html.erb. That partial puts a <iframe sandbox="allow-scripts"> on the page and adds a document--wide modifier class so the paper fills most of the viewport.

6

The iframe streams the stored copy. A new endpoint, GET /documents/:id/content/, picks the renderer from the version's content type. For HTML it wraps current_version.content.annotated_html in HtmlFrameDocument and returns it with no layout. No parsing happens at render time — the ids in the stream are exactly the ids in the database.

Why the ids are baked in at parse time

This is the key decision, so it deserves its own box.

The rule. Block ids are random. If we parsed the file again at render time, the random ids would differ from the ones comments point to. So the id-annotated copy is made once, at parse time, and stored. the content endpoint only streams it back.

Why an attribute, not id=? The file may already use id for its own links and styles. data-docnotate-block cannot collide with anything the author wrote.

What counts as a "block"

A comment anchors to a block, so the parser must decide which elements are blocks. Three lists in HtmlParser decide it:

  • Block tags — p, h1..h6, li, div, table, pre, blockquote and more. These always get anchors.
  • Inline tags — a, span, strong, em, code and friends. These never get an anchor of their own; they stay inside their parent block.
  • Skipped tags — script, style, svg, template. Never touched. The file's own code passes through untouched.

An element that is on no list gets an anchor only if it directly holds visible text and no block ancestor exists — a bare <b>bold text</b> at the top of the body becomes a block; the same tag inside a paragraph does not.

def parse
  document = Nokogiri::HTML5.parse(@content)
  @nodes = []
  @used_block_ids = Set.new

  walk(document.at("body"), parent_id: nil, inside_block: false)

  @annotated_html = document.to_html
  @nodes
end

def register_block(element, parent_id:)
  node_id = unique_block_id                      # "block-" + SecureRandom.hex(4)
  element["data-docnotate-block"] = node_id      # painted into the stored copy

  @nodes << { id:, document_version_id:, parent_id:, position:,
               node_type: node_type_for(element), heading_level:,
               node_id:, content: block_text(element), ... }

  walk(element, parent_id: db_id, inside_block: true)  # nested blocks still register
end
What stays the same: versioning, staleness detection, TOC extraction from the node tree, the Comment schema, and the whole markdown path. The bridge code is inert on markdown pages.

4. Walk through it — Part B: comments and highlights

The iframe holds the user's text but holds no app state. The parent page holds all state but holds no text. They must cooperate. The design rule:

The iframe is a dumb viewer. The parent page owns every piece of comment UI and state. The iframe only reports what the user did (selection, clicks, scroll position) and paints marks it is told to paint. All commands travel as postMessage with a docnotate: prefix.

Why so strict? The iframe runs with sandbox="allow-scripts" and no allow-same-origin. The browser calls that an opaque origin: the frame cannot read the app's DOM, cookies, or storage. That protects the app from whatever the file's scripts do — but it also means the app cannot reach into the frame. postMessage is the one door, and the bridge locks it from both sides.

The two participants

The bridge is the doorman: it checks who sent each message and converts coordinates between the two documents.

The full life of one comment

Rows 1–2 create a comment. Rows 3–4 turn the stored comment back into a visible highlight. The loop repeats after every edit, resolve, or delete.

1

Handshake. The client is injected into the frame at serve time. It cannot know when the parent's listener appears, so it posts docnotate:ready every 250 ms until the bridge answers. The bridge buffers its outgoing messages until ready, then flushes them. A comment payload can never arrive before the listener exists.

2

Selection. The user selects text inside the frame. On mouseup, the client runs the same anchor math as markdown — it lives in app/javascript/utils/text_anchors.js, shared by both paths. It finds the leaf blocks under the selection and computes offsets within them. Then it wraps the selection in a temporary green <mark> and posts docnotate:selection with the anchors plus the selection's frame-relative rectangles.

3

Toolbar and form — unchanged. The bridge converts frame-relative rectangles to page coordinates by adding the iframe's own offset. Then it dispatches a Stimulus event into the existing text-selection controller, which shows the "Add Note" toolbar and fills the same hidden fields: start_block_id, end_block_id, offsets, text.

4

Comment creation — unchanged. The form posts to /documents/:id/comments as it always has. Rails stores the comment against the current version. Because step 2 produced the same anchor format against the same node rows, the comment needs no special handling.

5

Highlights come back down. After any Turbo update, the payload JSON in #comment_payload_source reloads, and the bridge pushes docnotate:applyComments into the frame. The client clears its old marks, then for each comment walks the blocks between start_block_id and end_block_id, splits text nodes at the stored offsets, and wraps the covered text in <mark class="document__comment-highlight">. Same algorithm as the markdown highlighter, executing inside the frame.

6

Click, popover, navigation. Clicking a mark posts docnotate:markClick with the comment id and the mark's rectangle; the bridge opens the existing popover at the translated position. Comment nav arrows send docnotate:scrollTo; the client scrolls the mark into view inside the frame — the frame has its own scrollbar, so the parent never scrolls.

7

TOC and scroll tracking. On scroll inside the frame, the client reports heading positions; the parent's table-of-contents controller highlights the current section. TOC links go down as docnotate:scrollTo with a block id.

Step 1 · User selects text in the frame → event goes up app/javascript/html_frame/client.js 
document.addEventListener("mouseup", handleMouseUp)

function handleMouseUp() {
    const selection = window.getSelection()
    const selectedText = selection.toString().trim()
    if (!selectedText || selection.rangeCount === 0) return

    const range = selection.getRangeAt(0)
    const blocks = selectedBlocks(range)   // shared math from utils/text_anchors.js
    if (blocks.length === 0) return

    const { startOffset, endOffset } = computeBlockOffsets(range, blocks[0], blocks.at(-1))

    activeMarks = highlightRange(range, document.body)  // temporary green preview
    selection.removeAllRanges()

    postToParent({                       // window.parent.postMessage
        type: "docnotate:selection",
        blockIds: blocks.map(blockIdOf), // e.g. ["block-a1b2c3d4"]
        startOffset, endOffset,          // offsets inside those blocks
        selectedText, prefixText, postfixText,
        rects: markRects()               // frame-relative rectangles
    })
}
Step 2 · The bridge validates, translates, and re-dispatches app/javascript/controllers/iframe_bridge_controller.js 
window.addEventListener("message", this.boundReceive)

receive(event) {
    // only accept messages from OUR frame, arriving from its opaque origin
    if (event.source !== this.frameTarget.contentWindow || event.origin !== "null") return

    switch (event.data?.type) {
        case "docnotate:selection": this.handleSelection(event.data); break
        // ...ready, marksApplied, markClick, headings, ...
    }
}

handleSelection(message) {
    const rect = lastRect(message.rects)
    this.dispatch("selection", { detail: {
        blockIds: message.blockIds, startOffset: message.startOffset,
        endOffset: message.endOffset, selectedText: message.selectedText,
        ...this.anchorFor(rect)          // ← frame coords become page coords here
    } })
}

anchorFor(rect) {
    const frameBox = this.frameTarget.getBoundingClientRect()
    const paperBox = this.element.getBoundingClientRect()
    return { left: frameBox.left - paperBox.left + rect.right,
             top:  frameBox.top  - paperBox.top  + rect.bottom }
}

The dispatch("selection", ...) fires a Stimulus event. The wrapper's data-action routes it to the existing text-selection#showFromFrame — the HTML path enters the old flow at the same door markdown uses.

// parent: re-read the payload from the Turbo-replaced <script> tag and send it down
pushComments() {
    this.send({ type: "docnotate:applyComments", comments: this.currentComments() })
}

currentComments() {
    const source = this.element.querySelector("#comment_payload_source")
    return JSON.parse(source.textContent).current ?? []   // current version only
}
// frame: receive and paint
window.addEventListener("message", event => {
    if (event.source !== window.parent) return
    if (event.data?.type === "docnotate:applyComments")
        applyComments(event.data.comments)
})

function applyComments(comments) {
    unwrapHighlights(commentMarks, document.body)   // clear old marks first
    commentMarks = []

    comments.forEach(comment => {
        const startBlock = blocksById.get(comment.start_block_id)  // data-docnotate-block
        const endBlock   = blocksById.get(comment.end_block_id)
        if (!startBlock || !endBlock) return
        commentMarks.push(...applyCommentMarks(comment, blocks, startBlock, endBlock))
    })

    postToParent({ type: "docnotate:marksApplied", ... })  // parent rebuilds the nav
}

From here the loop closes: marksApplied tells the parent which comments are visible, the comment nav and copy features update, and every later edit/resolve/delete replays steps 4–5 with a fresh payload.

Show how a highlight is restored inside the frame app/javascript/html_frame/client.js 
function applyCommentMarks(comment, blocks, startBlock, endBlock) {
    // every block between the two anchors is covered
    const span = blocksBetween(blocks, startBlock, endBlock)

    return span.flatMap((block, index) => {
        // first and last blocks use the stored offsets; middle blocks are fully covered
        const from = index === 0 ? comment.start_offset : 0
        const to   = index === span.length - 1 ? comment.end_offset : textLength(block)
        if (from >= to) return []
        return wrapTextRange(block, from, to, comment.id)
    })
}

function wrapTextRange(root, from, to, commentId) {
    // walk text nodes, split at the offsets, and replace the middle with 
    const pieces = []
    let cursor = 0, textNode
    const walker = document.createTreeWalker(root, NodeFilter.SHOW_TEXT, null, false)
    while ((textNode = walker.nextNode()) !== null) {
        const overlapStart = Math.max(from, cursor)
        const overlapEnd = Math.min(to, cursor + textNode.textContent.length)
        if (overlapStart < overlapEnd) pieces.push({ textNode, overlapStart, overlapEnd, cursor })
        cursor += textNode.textContent.length
    }
    return pieces.map(p => {
        p.textNode.splitText(p.overlapEnd - p.cursor)   // cut after
        const highlighted = p.textNode.splitText(p.overlapStart - p.cursor)  // cut before
        const mark = document.createElement("mark")
        mark.className = "document__comment-highlight"
        mark.dataset.commentId = commentId
        mark.textContent = highlighted.textContent
        p.textNode.parentNode.replaceChild(mark, highlighted)
        return mark
    })
}
Trust note: the file's own scripts run inside the frame. The sandbox stops them from touching the app, from navigating the top page, and from sending forms — but they could still fetch remote resources. That tradeoff is accepted because these files come from our own tooling.

How the existing controllers learned to work remotely

The markdown paper lets controllers touch .document__content directly. The HTML paper sets data-comment-*-remote-value="true" on the wrapper. With that flag:

  • comment-highlight stops painting marks itself. It reads the marked comment ids from the frame's marksApplied report and builds the nav from them. Scrolling dispatches scrollTo to the bridge.
  • comment-popover positions from bridge-translated rectangles and repositions when the frame reports the focused mark's new place on scroll.
  • comment-copy learns which comments actually have visible marks (from receiveAnchors), so "copy" matches what the user sees.
  • table-of-contents updates its active section from iframe-bridge:headings events and navigates via table-of-contents:navigate → scrollToBlock.

Known limits, on purpose

  • Relative assets. The frame loads from /documents/:id/content/, so relative URLs such as diagram.png resolve to /documents/:id/content/*path. That route serves only allowlisted asset extensions (images, CSS, JS, fonts, audio, video) from the document's own directory, after realpath checks. Documents, hidden files, and anything outside the directory return 404. Web fonts may still fail, because browsers fetch them with CORS and the app sends no CORS headers.
  • Stored copy cost. Each html_contents row holds roughly one extra copy of the file per version. Fine for kilobyte-scale explainers.
  • Markdown width. Markdown keeps its 900px reading width; only HTML gets the wide paper.

6. Common confusions

"We render the file twice." No. The file is parsed once, at open time. The content endpoint streams the stored, id-annotated copy. That is the whole point of storing it — ids must not be redrawn, or every highlight would desync.
"The anchors use id= like markdown." Not for HTML. Markdown paints id="block-…" because it rebuilds the DOM from the node tree. HTML files keep their own ids, so anchors go on data-docnotate-block. Both values share the same block-… format and the same selector logic via blockIdOf().
"Comments are stored differently for HTML." They are not. Same columns, same POST endpoint, same payload JSON. The only HTML-specific storage is the html_contents row that holds annotated_html, linked from the version as its content.
"Can the frame talk to the app page directly?" No, and that is the safety property. Opaque origin means no DOM access, no cookies, no shared storage. The bridge also rejects any message whose event.source is not the frame and whose origin is not "null" — the value browsers give opaque-origin frames.
"What if the file's script crashes?" The app page survives. The frame stops reporting, the parent UI just shows a read-only document. The bridge's handshake means a restart of the frame re-syncs automatically.

7. Recap

  • Parse once, tag blocks. HtmlParser adds data-docnotate-block to every block and builds the same DocumentNode rows markdown builds — in one transaction, saved as the version's HtmlContent.
  • Render untouched. The iframe streams the stored copy through the content endpoint. The file's own CSS and JS keep working; the app's CSS cannot leak in, and the file's CSS cannot leak out.
  • One door. A typed docnotate: postMessage protocol, validated by the bridge. Events flow up, commands flow down, and a ready handshake prevents races.
  • Parent owns the UI. Toolbar, form, popover, nav, TOC, and archived inbox are the existing components; only DOM-touching steps delegate through the bridge.
  • Markdown path untouched. show.html.erb simply branches; the old paper lives in its own partial, byte-for-byte in behavior.
